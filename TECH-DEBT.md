# Dívidas Técnicas Conhecidas

Registro organizado de problemas conhecidos, não urgentes o suficiente para bloquear a feature em
andamento, mas que devem ser resolvidos antes de crescerem. Identificadores de código e endpoints
seguem em inglês; a descrição segue em português (mesmo padrão do `README.md`).

| # | Item | Impacto | Onde | Quando resolver |
|---|---|---|---|---|
| 1 | Contagem de séries ("N séries") ausente no card de exercício | O protótipo (Claude Design) mostra a contagem; hoje o card só exibe nome. Card menos informativo do que o design previa. | `exercise-row.component.ts` | Quando o backend expuser o campo no `GET /exercises/{divisionId}` (hoje omitido por YAGNI — não inventar campos de contagem no frontend, mesma regra já aplicada em `divisions`). |
| 2 | Erro silencioso ao carregar divisões | Se `GET /divisions` falhar, o dashboard mostra o empty-state ("Nenhuma divisão cadastrada ainda"), que é uma mentira — pode haver divisões salvas. Mesmo bug corrigido em `ExercisesComponent` nesta branch. | `DashboardComponent.loadDivisions()` | Replicar o padrão de `ExercisesComponent.loadExercises()` (signal `loadError` + terceiro ramo no template) na próxima vez que o `DashboardComponent` for tocado. |
| 3 | Falha de exclusão sem feedback ao usuário | Em `DashboardComponent.confirmDelete()`, `ExercisesComponent.confirmDelete()` e `SetsComponent.confirmDelete()`, o handler de erro só reseta `isDeleting`; o diálogo de confirmação continua aberto sem nenhuma mensagem explicando por que a exclusão falhou. | `dashboard.component.ts`, `exercises.component.ts`, `sets.component.ts` | Adicionar um `deleteError` (mesmo padrão de `formError`) exibido no `ConfirmDialogComponent` quando a exclusão falhar. |
| 4 | Divisões vivem em `features/dashboard/`, não em `features/divisions/` | Inconsistente com `features/exercises/` e `features/sets/` — quebra a promessa do `CLAUDE.md` de organização por fatia de domínio. | `features/dashboard/` | Extração maior (mover componentes + specs, ajustar rota); avaliar quando o dashboard ganhar mais responsabilidades além de divisões. |
| 5 | `npm audit`: 18 high / 1 critical | Todas as vulnerabilidades estão em `devDependencies` (`vite`/`vitest`/`esbuild`, toolchain de build/teste) — não afetam o bundle de produção. Nenhuma dependência nova foi adicionada nesta branch (o número subiu por atualização do banco de advisories, não por dependência nova). | `package.json` (devDependencies) | Rodar `npm audit fix` (ou `--force` com testes completos) numa tarefa dedicada de manutenção, fora do ciclo de uma feature. |
| 6 | Sem testes E2E | A cobertura é 100% unitária (componentes/serviços isolados com mocks). Nenhum teste exercita o fluxo real de navegação do usuário (login → dashboard → abrir divisão → abrir exercício → CRUD de série). | projeto todo | Avaliar Playwright/Cypress quando o número de fluxos críticos justificar o investimento (YAGNI até lá). |
| 7 | "Segurar para repetir" (press-and-hold) ausente nos botões `−` / `+` | O protótipo repete o incremento ao segurar o botão (380ms de espera, depois a cada 90ms). Hoje cada ajuste exige um clique — subir a carga de 0 para 100kg com incremento 2.5 custa 40 cliques. | `stepper-field.component.ts` | Adiado por YAGNI (não estava no escopo pedido). Implementar com `pointerdown`/`pointerup`/`pointerleave` + limpeza no `DestroyRef`; exige um ciclo TDD com fake timers. |
| 8 | `sets.component.ts` acima do limite de linhas | 209 linhas contra o limite de 150 do `CLAUDE.md` para `.ts` de componente (o `SetsHeaderComponent` já foi extraído e reduziu de 256). O `exercises.component.ts` tem o mesmo problema (242). | `sets.component.ts`, `exercises.component.ts` | Extrair a orquestração de estado (carregar/criar/excluir/persistir) para um serviço de feature com signals, ou dividir a lista num componente próprio. Vale fazer nos dois arquivos de uma vez, para o padrão ficar consistente. |
| 9 | Falha ao renomear série sem feedback ao usuário | `SetsComponent.onRenameSet()` não trata o erro: se o `PATCH` falhar, o card volta ao modo leitura exibindo o nome antigo, sem avisar que a alteração não foi salva. | `sets.component.ts` | Mesma solução do item 3 — quando houver um padrão de feedback de erro inline, aplicar aqui também. |
